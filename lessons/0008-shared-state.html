Shared state — one currency, many consumers

Change USD to MYR in the navbar and prices update across the app. One small Zustand store connects that single interaction to every component that cares.

Tied to your mission Shared state appears whenever distant components must agree: theme, logged-in user, watchlist, or display currency. You need to know who owns it, who changes it, and who re-renders because of it.

Why local state is not enough

If Navbar used useState('usd'), only the navbar would know the selection. ListPage and CoinPage are not its children, so passing the value as props would require threading it through App. This is called prop drilling.

A store gives unrelated components one shared source of truth:

Navbar ──writes──┐
                 ├── useSettings store
ListPage ──reads─┤
CoinPage ──reads─┘

The store has state and actions

Open src/stores/settings.ts:

interface SettingsState {
  currency: FiatCode
  setCurrency: (currency: FiatCode) => void
}

export const useSettings = create<SettingsState>()(
  persist(
    (set) => ({
      currency: 'usd',
      setCurrency: (currency) => set({ currency }),
    }),
    { name: 'crypto-settings' },
  ),
)
  • currency is the shared value.
  • setCurrency is an action: the approved way to change it.
  • set({ currency }) merges the new value into the store and notifies subscribers.
  • create<SettingsState>() checks that the implementation matches the interface.

Selectors subscribe components

Navbar selects both the value and action:

const currency = useSettings((s) => s.currency)
const setCurrency = useSettings((s) => s.setCurrency)

The callback is a selector. A component subscribed to currency re-renders when currency changes. A component selecting only setCurrency does not need to re-render for an unrelated store value.

ListPage selects currency, then uses it in its query:

const currency = useSettings((s) => s.currency)
const { data } = useMarket(currency)

Store update → page re-render → query key changes from ['market', 'usd'] to ['market', 'myr'] → MYR data loads. Lesson 7's lifecycle begins again.

Persist survives a reload

The persist middleware saves the store under crypto-settings in browser storage. Refresh the page and your currency remains selected. Zustand restores it when the app starts.

Remember Zustand holds the live in-memory state. persist copies it to browser storage so it can be restored later.

Your edit — protect the shared boundary

The supported currencies already form a union type in src/services/types.ts. Make the store accept only that type:

import type { FiatCode } from '../services/types.ts'

interface SettingsState {
  currency: FiatCode
  setCurrency: (currency: FiatCode) => void
}

A browser select still produces a general string, so validate it before calling the typed action in Navbar.tsx:

import { isFiatCode } from '../services/coingecko.ts'

function handleCurrencyChange(value: string) {
  if (isFiatCode(value)) setCurrency(value)
}

onChange={(e) => handleCurrencyChange(e.target.value)}

isFiatCode is a type guard. Inside the if, TypeScript narrows value from any string to a supported FiatCode. Invalid values never enter shared state.

Trace one click

  1. User selects MYR; the browser emits the string 'myr'.
  2. isFiatCode validates and narrows it.
  3. setCurrency('myr') updates the Zustand store.
  4. persist saves it; subscribed pages re-render.
  5. Query keys change and CoinGecko receives vs_currency=myr.
  6. Prices render with RM.
