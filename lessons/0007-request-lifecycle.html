The request lifecycle — URL to chart

Open /coin/bitcoin and several files cooperate in sequence. Today you will trace that sequence instead of reading each file in isolation.

Tied to your mission Most maintenance starts with a visible symptom: a URL fails, a spinner never stops, or a chart is blank. Tracing the value through each layer tells you which file owns the problem.

1. The route chooses the page

In src/App.tsx, wouter compares the browser URL with each route:

<Route path="/coin/:id" component={CoinPage} />

The colon makes :id a route parameter. For /coin/bitcoin, wouter renders CoinPage and records id = 'bitcoin'.

2. The page reads inputs

At the top of src/pages/CoinPage.tsx:

const { id } = useParams()
const currency = useSettings((s) => s.currency)
const [days, setDays] = useState<number>(7)

The request has three inputs from three places:

  • id comes from the URL.
  • currency comes from the shared settings store.
  • days comes from this page's local state.

3. Hooks describe two requests

const coinQuery = useCoin(id ?? '')
const chartQuery = useMarketChart(id ?? '', currency, days)

The detail request needs only the coin ID. The chart request needs all three inputs. id ?? '' means “use the ID unless it is null or undefined; otherwise use an empty string.”

Follow the chart into src/hooks/useMarketChart.ts:

queryKey: ['marketChart', id, currency, days],
queryFn: () => fetchMarketChart(id, currency, days)

The key is a dependency list and cache address. Clicking 30d changes days, which produces a new key, so TanStack Query requests and caches a different chart.

4. The service builds the HTTP request

src/services/coingecko.ts turns those typed values into a URL:

const params = new URLSearchParams({
  vs_currency: currency,
  days: String(days),
})
return request(`/coins/${encodeURIComponent(id)}/market_chart?${params}`)

URLSearchParams handles query-string formatting. encodeURIComponent makes the path value safe. The shared request<T> helper performs fetch, rejects bad HTTP responses, and parses JSON.

5. Query state drives the render

The Promise settles and TanStack Query updates chartQuery. React re-renders the page:

isLoading  → show “Loading chart…”
isError with no data → show an error and retry action
data       → render <PriceChart prices={...} />

This is the complete loop: an input changes, the query key changes, a request runs, query state changes, and React renders the matching UI. Checking !chartQuery.data avoids replacing a usable cached chart when only a background refresh fails.

Your edit — complete the lifecycle

The page already handles chart loading and success, but not chart failure. In CoinPage.tsx, after the loading block, add:

{chartQuery.isError && !chartQuery.data && (
  <div className="flex h-72 flex-col items-center justify-center gap-3 text-red-300">
    <p>Could not load chart data.</p>
    <button
      type="button"
      onClick={() => chartQuery.refetch()}
      className="rounded-md border border-red-800 px-3 py-1.5 text-sm transition-colors hover:bg-red-950/40"
    >
      Try again
    </button>
  </div>
)}
  1. Open a coin page and use DevTools to switch the network offline.
  2. Change the day range. The chart request fails and the new error state appears.
  3. Go online and click Try again. The same query runs again and success replaces the error.

Debug from the symptom

  • Wrong page opens → inspect App.tsx and the link that built the URL.
  • Wrong coin loads → inspect useParams and the query key.
  • Wrong endpoint or parameters → inspect coingecko.ts.
  • Request succeeds but UI is wrong → inspect CoinPage, types, and child props.
