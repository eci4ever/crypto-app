State — when a component remembers

Props fall from the parent like rain. State is the water the component itself holds. It's what makes the search box retain your typing — and what will finally explain the heart button.

Tied to your mission Every interactive feature you'll maintain — the search box, the day-range buttons, the portfolio form — is state. Your very first contribution (the {coins.length} count) only works because query state re-renders the page on each keystroke.

See state in the wild

Open src/pages/ListPage.tsx, near the top:

const [query, setQuery] = useState('')
const [filter, setFilter] = useState<Filter>('all')

Read the first line: "a state variable called query, starting as an empty string, with a setter called setQuery." That's array destructuring: useState returns two things — the value and the setter — and the brackets pull them apart.

This is the moment everything locks together. Every typing session in the search box is those two lines in action:

<input
  value={query}
  onChange={(e) => setQuery(e.target.value)}
/>
  • Read: value={query} shows the current state.
  • Write: onChange fires on every keystroke, calls setQuery(e.target.value), and React re-renders the page with the new text.

That re-render re-runs coins = useMemo(…) with the new query — which is exactly why the count in your Lesson 2 contribution shrinks as you type.

Why not just a variable?

The temptation is let query = ''. The problem: every render recreates local variables. The component re-renders, let query is born fresh at '', and the page forgets what you typed — a broken search box.

State is the exception: it survives re-renders, and changing it is what causes a re-render in the first place. That one property is the entire reason React exists.

The change cycle

  1. User types "bi" ⟶ onChange fires
  2. setQuery('bi') ⟶ React notes the change
  3. React re-renders the component ⟶ query is now 'bi'
  4. The input value, the filtered coins, and your {coins.length} all refresh

Write a setter, and the rest follows. That's the mental model.

Typed state

State can carry a generic type, from Lesson 3:

const [days, setDays] = useState<number>(7)      // CoinPage
const [filter, setFilter] = useState<Filter>('all') // ListPage, union type

<Filter> means the setter only accepts 'all' or 'watchlist' — pass anything else and tsc fails. State inherits the whole safety net.

Local vs shared state

The heart button never calls useState — it uses Zustand (src/stores/watchlist.ts). One sentence to file this away:

Rule of thumb useState = state one component cares about (a search box, a selected day). A store = state many components share (the watchlist hearts, the currency dropdown, the portfolio). Put state as low as it will go; lift it only when siblings need it.

Your edit — the skill

Add a Clear button that appears only while you're searching — the classic pattern, and it exercises reading state, writing state, and the conditional rendering from Lesson 2.

In src/pages/ListPage.tsx, right after the search <input … />, add:

{query && (
  <button
    type="button"
    onClick={() => setQuery('')}
    className="rounded-md bg-slate-800 px-3 py-2 text-sm text-slate-200 hover:bg-slate-700"
  >
    ✕ Clear
  </button>
)}
  1. Save. Type in the search box — the Clear button appears.
  2. Click it. setQuery('') empties the state; the button vanishes, the full 50-list returns.
  3. Trace it: query truthy ⟶ button rendered; query empty ⟶ nothing. State drove the render.
