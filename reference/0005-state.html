State — when a component remembers

Props are handed in; state is remembered inside. State changes trigger React to re-render the component with the new value.

The useState hook

const [query, setQuery] = useState('')

useState returns a pair: the current value and a setter. The convention is to name them [thing, setThing] — that's array destructuring, from the core JS you know.

Read and write

// read — use it anywhere in render
<input value={query} onChange={(e) => setQuery(e.target.value)} />

{query.length > 0 && (
  <button onClick={() => setQuery('')}>Clear</button>
)}
  • value={query} — the input shows the current state (controlled input).
  • setQuery(e.target.value) — every keystroke writes new state; React re-renders.
  • setQuery('') — reset it.

Why not a plain variable?

let query = ''          // reset to '' every render — useless
const [query, setQuery] = useState('')  // survives; change re-renders

A plain variable forgets its value on every re-render. State is the thing that survives renders and triggers them.

Typed state

const [days, setDays] = useState<number>(7)
const [filter, setFilter] = useState<Filter>('all')

The generic <T> sets the value's type. Filter is a union ('all' | 'watchlist'), so setting an invalid value fails type-checking.

Local vs shared state

  • Local state (useState) — belongs to one component: a search box, a selected day range.
  • Shared state (Zustand stores in this repo) — needed by many components: watchlist, portfolio, chosen currency.

Rule of thumb: put state as low as possible. Only lift it up when siblings need to share it.
