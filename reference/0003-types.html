Types — TypeScript's safety net

A type describes the shape of data. TypeScript checks every type in your code before it runs — in your editor and at npm run build time — and refuses to build if something doesn't match.

The everyday primitives

let name: string    // text
let price: number   // any number
let loading: boolean // true or false

Reading a function signature

export function formatPrice(price: number, code: string): string {
  // … params typed inside, return type after ):
}
function(format price   code          ) return
        ↓        ↓      ↓              ↓
        name    type    type           type

Read it left to right: "formatPrice takes a number called price and a string called code, and returns a string."

Describing whole objects — interfaces

interface CoinMarket {
  id: string
  symbol: string
  name: string
  current_price: number
  price_change_percentage_24h: number
  sparkline_in_7d: { price: number[] } | null
}

An interface says: "an object with these fields, of these types." The | null means "this field can also be absent/empty." number[] means "an array of numbers."

Inference — most types you don't write

const count = 50      // TS already knows: number
const title = "Crypto" // TS already knows: string

TypeScript infers types from the value on the right. You only write annotations where it can't infer — function parameters and return types.

Why you'll care as a maintainer

Types are one way, upstream. If you change formatPrice(price: number, code: string) to code: number, tsc instantly lists every call site that now passes a string — including calls you forgot about. The type error is a to-do list, not an accusation.

src/utils/format.ts:14:57 - error TS2345
Argument of type 'number' is not assignable to parameter of type 'string'.
